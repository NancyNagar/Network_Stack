\paragraph{Setup notes.}
Four Ubuntu VMs (client, r1, r2, server) with four isolated internal networks
(LAN~A, LAN~B, LAN~C, Link~D). Each machine is configured only by its
\cmd{netcfg/*.sh} script, run once as root after setting \cmd{rp\_filter=1} on every
interface. Before running our programs on the VMs we add (by hand, \emph{not} in
\cmd{netcfg} or in our code, as allowed on Piazza) an iptables rule that drops the
RSTs the kernel would otherwise send for our raw-socket connections:
\begin{lstlisting}
client$ sudo iptables -A OUTPUT -p tcp --tcp-flags RST RST --sport 61000:65535 -j DROP
server$ sudo iptables -A OUTPUT -p tcp --tcp-flags RST RST --sport 8080:8083 -j DROP
\end{lstlisting}
Our server is therefore always started with a port in 8080--8083.

\section*{R2. traceroute in both directions}

Expected output (\cmd{traceroute -n}, default UDP probes):
\begin{lstlisting}
client$ traceroute -n 10.10.3.10          server$ traceroute -n 10.10.1.10
 1  10.10.1.1   (r1, LAN A)                1  10.10.3.1   (r2, LAN C)
 2  10.10.4.1   (r2, Link D)               2  10.10.1.10  (client)
 3  10.10.3.10  (server)
\end{lstlisting}

\textbf{Client $\to$ server.}
\emph{Hop 1:} the TTL=1 probe goes to r1 (the client's default gateway). r1 sends ICMP
Time Exceeded back out of LAN~A, so its source is r1's LAN~A address 10.10.1.1.
\emph{Hop 2:} the TTL=2 probe is forwarded by r1 to r2 over LAN~B, where it expires. r2
builds an ICMP Time Exceeded addressed to 10.10.1.10. Linux picks the source address of
an ICMP error from the route used to send it (\cmd{icmp\_errors\_use\_inbound\_ifaddr=0}),
not from the interface the probe arrived on. r2's route to 10.10.1.10 is the \cmd{/32} via
Link~D, so the reply leaves on IF\_D with source 10.10.4.1. That is why r2 appears as
10.10.4.1 and not as 10.10.2.2 (the address the probe actually reached). The client accepts it on
its Link~D interface (10.10.4.1 is directly connected there).
\emph{Hop 3:} the probe reaches the server, which answers ICMP Port Unreachable from 10.10.3.10;
that reply also travels server$\to$r2$\to$client over Link~D.

\textbf{Server $\to$ client.}
\emph{Hop 1:} r2 (server's gateway) drops the TTL=1 probe and replies out of LAN~C, source
10.10.3.1. \emph{Hop 2:} r2 forwards the TTL=2 probe straight over Link~D to the client
(\cmd{/32} route), and the client replies with Port Unreachable from the probed address 10.10.1.10.
r1 never appears because it is not on the server$\to$client path.

\textbf{Why the directions differ.} The routing is asymmetric on purpose (A2/A3): the
client's only non-connected route is via r1, while r2's host route sends everything for the
client over Link~D. So the forward path has three hops and the reverse path two, and in
the forward trace r2 shows up with its Link~D address because its ICMP reply goes
back over the reverse path.

\section*{R3. Reverse-path filtering}

The value the kernel actually uses on an interface is
$\max(\cmd{conf.all.rp\_filter},\ \cmd{conf.<if>.rp\_filter})$. All machines start
with 1 everywhere and our scripts never touch \cmd{conf.all}, so it stays 1. Setting an
interface to 0 would therefore have no effect ($\max(1,0)=1$); the only way to relax
one interface is loose mode (2), which accepts a packet if its source is reachable via
\emph{any} interface. Strict mode (1) requires that the best route back to the source
leaves through the interface the packet arrived on.

All of this is in \cmd{src/tcp.py}. Sequence numbers are compared modulo $2^{32}$.

\paragraph{Retransmission.}
We keep one retransmission timer for the oldest unacknowledged byte (\cmd{snd\_una}).
RTT is sampled on one segment at a time and smoothed as in RFC~6298
($\mathit{srtt}\leftarrow\frac78\mathit{srtt}+\frac18 r$,
$\mathit{rttvar}\leftarrow\frac34\mathit{rttvar}+\frac14|\mathit{srtt}-r|$), with
$\mathit{RTO}=\min(\mathit{srtt}+\max(4\cdot\mathit{rttvar},\,200\mbox{ ms}),\ 1\mbox{ s})$;
the initial RTO is 1\,s. Karn's algorithm: the pending RTT sample is discarded whenever
anything is retransmitted, so retransmitted segments are never timed. When the timer
expires we double the RTO (still capped at 1\,s), set \cmd{snd\_nxt} back to \cmd{snd\_una}
and resend the first segment; the rest is then resent go-back-N style as the window
opens. If data is outstanding and nothing new has been acknowledged for 10\,s, the
connection is aborted. Fast retransmit: on the third duplicate ACK the first
unacknowledged segment is resent immediately. Before that, the first two duplicate ACKs each allow
one extra new segment beyond \cmd{cwnd} (limited transmit, RFC~3042), so a
small window can still produce three dup ACKs. SYN/SYN-ACK are retried every 1\,s for 8\,s,
and our FIN is retransmitted until ACKed, giving up after 2\,s.

\paragraph{Out-of-order buffering.}
In-order data is appended to the receive buffer and \cmd{rcv\_nxt} advances. A segment
that starts above \cmd{rcv\_nxt} but within our 65\,535-byte advertised window is stored in
a dictionary keyed by its sequence number (keeping the longer copy on duplicates). Bytes
below \cmd{rcv\_nxt} are trimmed, so duplicates are delivered only once. Whenever the gap at
\cmd{rcv\_nxt} is filled, we repeatedly drain every buffered segment that now starts
at or below \cmd{rcv\_nxt}, trimming overlap, until no more progress is made. A peer FIN is
only consumed once \cmd{rcv\_nxt} reaches its sequence number. We send a cumulative ACK
for every data segment, including duplicates and out-of-order ones (no delayed ACKs).
These duplicate ACKs are what drive the sender's fast retransmit.

\paragraph{Congestion control.} Reno, with NewReno handling of partial ACKs.
Data in flight never exceeds $\min(\mathit{cwnd},\ \mbox{peer window})$.
\begin{itemize}\setlength\itemsep{0pt}
\item \emph{Slow start:} initial window 10\,MSS; while $\mathit{cwnd}<\mathit{ssthresh}$,
  each new ACK adds $\min(\mbox{acked},\ \mathrm{MSS})$.
\item \emph{Congestion avoidance:} each new ACK adds $\mathrm{MSS}^2/\mathit{cwnd}$
  (about 1\,MSS per RTT).
\item \emph{Fast recovery:} on the 3rd dup ACK, $\mathit{ssthresh}=\max(\mbox{flight}/2,\,2\,\mathrm{MSS})$,
  $\mathit{cwnd}=\mathit{ssthresh}+3\,\mathrm{MSS}$ and \cmd{recover} is set to the highest sequence sent.
  Each further dup ACK inflates \cmd{cwnd} by 1\,MSS. A partial ACK (below \cmd{recover})
  immediately retransmits the next hole and deflates \cmd{cwnd} by the amount acked (NewReno);
  a full ACK ends recovery with $\mathit{cwnd}=\mathit{ssthresh}$. A new fast retransmit is
  not started until \cmd{snd\_una} passes \cmd{recover}.
\item \emph{Timeout:} $\mathit{ssthresh}=\max(\mbox{flight}/2,\,2\,\mathrm{MSS})$,
  $\mathit{cwnd}=1\,\mathrm{MSS}$, recovery is cancelled, then slow start again.
\end{itemize}

\paragraph{Fairness measurements (namespace testbed).}
We reproduced the bottleneck described on Piazza: 10\,Mbit/s with 10\,ms delay and a
30-packet (45\,000\,B) FIFO on r2's Link~D egress, plus 10\,ms delay on r1$\to$r2 (netem +
tbf, with TSO/GSO/GRO off). $N$ of our client$\leftarrow$our-server flows run at the same time as $N$
curl$\leftarrow$\cmd{python3 -m http.server} flows (kernel TCP sender, CUBIC), downloading
an 80\,MB file. Throughput is counted at the client over a 20\,s window after 5\,s of warm-up.
Jain's index is over all $2N$ flows.

The link is always fully used and no flow starves. With a single flow of each kind the split is reasonably fair, but our flows get
more than their share as $N$ grows (about $2\times$ the curl flows at $N=3$). We think the cause is
where the drops land, not a more aggressive window rule. Our receiver ACKs every
segment, so our sender is clocked out one segment per ACK and its packets spread over the RTT.
curl's receiver (the Linux stack) uses delayed ACKs. Each of its ACKs covers two or more
segments, so the kernel sender emits back-to-back bursts, and bursts are much more likely to
overflow a 30-packet tail-drop queue. At $N=3$ we measured about 1.8\,\% of our segments
lost/retransmitted against about 7\,\% for the curl flows (the qdisc dropped 1145 of
37\,181 packets overall). For loss-based TCP, throughput $\propto \frac{\mathrm{MSS}}{\mathit{RTT}\sqrt{p}}$,
so $\sqrt{7/1.8}\approx 2$, which matches the observed ratio. Per-ACK growth also helps us a
little: with one ACK per segment, Reno's $\mathrm{MSS}^2/\mathit{cwnd}$ rule gives the full
1\,MSS per RTT. So our control law is standard Reno, but the bottleneck penalises the
burstier kernel flows more.
